# SQL-архитектура ATADAN

## Принцип

Единственный источник данных админки — SQLite/D1. Серверные маршруты React/Vinext выполняют параметризованные SQL-запросы через D1. Браузер никогда не получает парольные хеши, соли, токены приглашений, закупочные цены другого уровня доступа или полную базу чужого менеджера.

Внешний BaaS для базы и авторизации не используется.

## Таблицы

| Таблица | Назначение |
| --- | --- |
| `staff` | сотрудники, роль, статус, PBKDF2-хеш, тема и профиль |
| `staff_sessions` | хеши восьмичасовых HttpOnly-сессий |
| `staff_invites` | одноразовые приглашения менеджеров |
| `leads` | исходные обращения с сайта |
| `lead_requests` | ключи идемпотентности заявок |
| `crm_customers` | карточки клиентов |
| `crm_deals` | сделки, этап, сумма, ответственный, версия |
| `crm_tasks` | задачи менеджеров с дедлайном |
| `crm_notes` | история заметок по сделке |
| `product_costs` | закупочная цена; доступна только owner |
| `product_overrides` | изменения и новые товары каталога |
| `news_posts` | изменения, публикации и архив новостей |
| `site_settings` | контакты, лизинг, переводы и замены медиа |
| `interest_events` | обезличенные просмотры страниц и моделей |
| `audit_logs` | журнал важных действий |
| `request_limits` | серверные лимиты попыток |

Денежные значения CRM хранятся целыми числами в тыйынах (`*_minor`). Это исключает ошибки двоичной арифметики. Записи сделок, задач, затрат и настроек имеют `version`; обновление выполняется только при совпадении версии и возвращает 409 при конфликте.

## Роли

| Возможность | owner | manager |
| --- | :---: | :---: |
| Все сделки и клиенты | Да | Нет |
| Только назначенные сделки, клиенты и задачи | Да | Да |
| Изменять этап своей сделки | Да | Да |
| Вернуть закрытую сделку | Да | Нет |
| Видеть себестоимость и маржу | Да | Нет |
| Редактировать каталог, новости и настройки сайта | Да | Нет |
| Приглашать и блокировать менеджеров | Да | Нет |
| Смотреть журнал действий | Да | Нет |
| Редактировать свой профиль и тему | Да | Да |

Права проверяются в API через `requireActor`. Скрытие кнопки в интерфейсе — только удобство, а не механизм безопасности.

## Поток заявки

1. Форма отправляет имя, телефон и выбранную модель с одноразовым `Idempotency-Key`.
2. Сервер проверяет источник запроса, размер JSON, honeypot, лимит частоты, телефон и существование модели.
3. Одна SQL-транзакция создаёт `leads`, `crm_customers`, `crm_deals` и `lead_requests`.
4. Повтор того же запроса возвращает существующий идентификатор и не создаёт дубликат.
5. На клиенте открывается WhatsApp, но SQL-запись уже сохранена независимо от результата открытия.

Старые заявки переносятся в CRM недеструктивным `INSERT OR IGNORE` внутри миграции 0002.

## Вход и приглашения

- Пароль хранится как PBKDF2-SHA256 с индивидуальной случайной солью и 100 000 итерациями.
- В cookie находится только случайный токен; в SQL хранится его SHA-256-хеш.
- Cookie: `HttpOnly`, `SameSite=Strict`, `Secure` на HTTPS, срок 8 часов.
- При блокировке менеджера все его сессии удаляются.
- Приглашение хранится только как хеш, действует 24 часа, создаёт роль `manager` и после использования помечается использованным.
- Сам токен передаётся в URL-фрагменте `#...`, поэтому не попадает в HTTP-запрос и access-log.

## Этапы сделки

`new → contacted → proposal → negotiation → won/lost`.

Для `won` обязательна ненулевая сумма продажи. Для `lost` обязательна причина. Менеджер не может повторно открыть `won` или `lost`; это действие доступно управляющему.

## Миграции и откат

Все изменения схемы добавляются новым SQL-файлом в `drizzle/` и применяются по порядку. Запрещено создавать таблицы в runtime-коде. Перед развёртыванием нужно сделать резервную копию базы и проверить миграцию локально.

Откат приложения выполняется возвратом на предыдущий commit. Миграции данных не удаляют старые таблицы или заявки; новые таблицы можно оставить совместимыми с предыдущей версией. Для необратимого изменения схемы требуется отдельная backup/restore-процедура, а не автоматический `DROP TABLE`.

## Где находится логика

- `db/schema.ts` — декларативная SQL-схема;
- `drizzle/*.sql` — миграции;
- `app/lib/admin-auth.ts` — пароль, сессии и роли;
- `app/api/admin/crm/route.ts` — сделки, задачи, затраты и команда;
- `app/api/admin/invites/route.ts`, `app/api/admin/join/route.ts` — приглашения;
- `app/api/leads/route.ts` — приём заявок в SQL;
- `app/api/admin/settings/route.ts` — общие настройки сайта;
- `app/lib/leasing.ts` — чистый расчёт графика лизинга.
